# Orchestrate on T3 Code

Orchestrate is written for Cursor's Task tool and cloud agents. In T3 every agent is local, and these tools take their place. Drop Orchestrate's `environment: "cloud"` placement, the `gt` stacker and `frontier.json` (no Graphite stacks here), and sub-coordinators until more than about 10 units are in flight. Default in-flight cap: 5, unless `project.md` sets another.

## Models

Call `orchestrator_capabilities` once per session. The output is large; save it and query it with `jq`. Use only a provider whose `canRunChildTask` is true. Claude models run on the Claude provider (now `claude_openrouter_shared`, ids like `claude-opus-5-5`, reasoning `{"effort": "xhigh"}`). Other families run on `codex` (ids like `openai/gpt-6.1-sol`, reasoning `{"reasoningEffort": "xhigh"}`).

## Spawn a worker

A worker is a top-level T3 thread in its own worktree. It can watch its own PR; a delegated child can't.

1. `t3_project_list` for the repo's `projectId`. Record it in `project.md`.
2. Save the brief to `<project home>/briefs/<unit>.md`. The brief is Orchestrate's template, preceded by these two lines and followed by the handoff:
   - Opening line, for a Claude worker: "Before any work, load `pstack:poteto-mode` with the Skill tool and follow it." For a Codex worker: `$poteto-mode`.
   - Environment line: "You run in T3 Code. A pstack role whose model your native subagent tool can't select runs through the t3-code `delegate_task` tool, not `codex exec`. Babysit your PR by calling `link_pull_request` and then `watch_pull_request` on your own thread and ending your turn; T3 wakes you, so don't use `/loop` or poll. `control-ui`, `control-cli` and `deslop` aren't installed here: use the repo's `verify-*` skill and skip `deslop`."
   - Handoff: "End each turn with a report in Orchestrate's REPORT shape. Never merge, and never start threads; send proposed follow-ups in your report."
3. `t3_thread_launch` with `projectId`, `title` `<ticket>: <goal>`, `message` = the brief, and `workspaceStrategy` `{"type": "worktree", "baseRef": "<default branch>", "branch": "<branch>", "startFromOrigin": true}`. Never omit the strategy: without it the worker runs in the shared checkout. Pass `modelSelection` only for a non-default model.
4. `orch unit add <unit> --track <track> --brief <path>`. Record the `threadId` in `<project home>/t3-threads.tsv` (`unit`, `threadId`, `cursor`). The launch has no retry key; if it errors, check `t3_thread_list` before launching again.

## Resume a worker

`t3_thread_send` with `mode: "auto"` and a `clientRequestId`. Start every message with "Stay in poteto-mode. If its SKILL.md is no longer in your context, reload `pstack:poteto-mode` with the Skill tool first." (Codex: `$poteto-mode`), then the output of `orch standing show`.

## Spawn a verifier

`delegate_task`, `mode: "async"`, `role: "review"`, on a model family different from the worker's, with a `clientRequestId` unique to the round. It runs in your checkout, so keep it read-only. Point it at the worker's worktree (`t3_worktree_list` with the worker's `threadId`) and the PR's head SHA. Each round is a fresh `delegate_task` carrying the brief, prior findings and responses; never continue one through its `childThreadId`. Its completion wakes this thread: `orch inbox push` it, then `orch ledger record <pr> <sha> <verdict> --evidence <report path> --verifier <model>` at the next drain.

## Drain

The scheduled drain is Orchestrate's watcher wake. Create it once with `schedule_task` (`{"type": "interval", "everyMs": 1800000}`, `bindToCurrentThread: true`) after checking `list_scheduled_tasks` for an existing one. Its prompt:

```
Coordinator drain (automated, not from the human). Check quiet hours in <project home>/project.md first; if inside them and the human hasn't messaged since they began, reply "quiet hours, paused" and stop. Otherwise run the Drain in the project-coordinator skill's references/t3.md for <project home>.
```

Each drain:

1. `t3_thread_list` with the `projectId`, following `cursor` until every thread in `t3-threads.tsv` is found. For each whose turn ended (`completed`, `failed`, `interrupted`), read its new output with `t3_thread_read` (view `messages`, `afterPosition` = stored cursor, each `nextPosition` until `hasMore` is false; recover truncated items with `itemId` and `textOffset`). Store the new cursor and `orch inbox push <threadId> <unit> <status>`.
2. A `waiting` thread is blocked. Get the exact question from `t3_pending_request_list` and `t3_pending_request_read`, or, when that list is empty, the pending approval from `t3_thread_read` view `activity`. `orch gate park` it and show it to the human word for word, with the options. Never answer it for them.
3. Run Orchestrate's drain over `orch inbox drain`. For each unit with an open PR: `list_thread_pull_requests` with the worker's `threadId` for state and head SHA (`orch unit set --pr --sha`). Run the project's bot-review steps from `project.md`. Spawn a verifier at each new head SHA. Relay blocking comments to the worker. Merge only under the merge rule in poteto-mode's `playbooks/opening-a-pr.md`.
4. Refill the window up to the cap with ready units.
5. `orch status`. If nothing changed, reply with one line. Otherwise give a 3–5 line summary leading with what needs the human. Send one `PushNotification` only when something newly needs the human.

Don't poll CI. Each worker watches its PR. Check CI once, just before a bot-review request or a merge.

## Close a worker

After its PR merges or the human drops it: `orch unit set <unit> --state done` (or `abandoned`), then `t3_thread_organize` with `action: "settle"`. T3 keeps the worktree; ask the human before `git worktree remove`.

Pin the coordinator thread with `t3_thread_organize` (`action: "pin"`).
